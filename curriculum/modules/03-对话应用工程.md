# 3. 对话应用工程

## 学习目标

做出可多轮对话的最小应用，而不是单次脚本。

完成标准：在同一次运行里对话能接着聊；密钥不出现在打印日志里。

### 3.1 消息角色与历史

**要点**

- `system` 放规则，通常在最前。不要每来一句用户话就换掉它。
- `user` 是用户这一次说的话。
- `assistant` 是模型上一轮的回复。放回历史时保持原样，不要替它改写。
- 顺序就是对话顺序。漏掉某一轮 `assistant`，模型就失去自己刚说过的话。

**练习**

手写含 `system` 的 3 轮消息列表。再写明：如果删掉中间那条 `assistant`，模型会跟丢哪一句它自己说过的话。

**自检**

- [ ] `system`、`user`、`assistant` 三种角色都用对了位置
- [ ] 能指出删掉中间回复后，具体跟丢的内容

**状态**（只勾一项）

- [ ] 进行中
- [ ] 已完成

<a id="3-2"></a>

### 3.2 流式输出、超时、重试、限流

**要点**

- 流式输出是边生成边显示。中途失败时，屏幕上可能只有半截文本。半截文本不要写进历史。
- 超时要设上限。超时后的重试要有次数上限。
- 限流（HTTP 429）可以等待后重试。密钥错误和参数错误重试没有意义。
- 只为网络失败、超时、限流重试。不要因为「内容不太好」就自动再请求一次。

**练习**

写下你的超时时间、最大重试次数，以及两份清单：哪些错误会重试，哪些错误直接告诉用户。

**自检**

- [ ] 密钥错误、模型名错误不在重试清单里
- [ ] 写明了半截流式输出不会被当成完整回复写入历史
- [ ] 重试次数是有限的

### 3.3 会话状态与日志

**要点**

- 先定保留上限，例如最多 8 轮用户发言，或一个 token 预算。
- 超长时丢掉最早的一对 `user` / `assistant`。`system` 保留。
- 日志可以记请求编号、耗时、token 数。不要记密钥，不要把环境变量整份打出来。
- 模型不会在进程结束后替你记住对话。这次运行内要接着聊，历史必须由你的程序保存并在下次请求里带上。

**练习**

做一个命令行对话。保留最近 8 轮用户发言；更早的用户轮次从请求里去掉，系统提示始终还在。连续聊过 8 轮后，再发一句，确认最早一轮已经不在发往模型的消息里。

**自检**

- [ ] 第 9 轮用户话进入时，最早一轮用户话已不在请求里
- [ ] 系统提示仍在请求最前
- [ ] 同一次运行中，后面的回复能接上前面的话题
- [ ] 在终端输出里搜不到密钥

**状态**（只勾一项）

- [x] 未开始
- [ ] 进行中
- [ ] 已完成
